# 改写例子：一句话需求 → 需求梳理块

三个真实形态的例子，覆盖三种典型缺口：**场景缺失**、**范围过载**、**判据缺失**。
每个例子后面的"要点"说明这次是哪个缺口在起作用，不要照抄输出格式里的措辞。

## 例 1：场景缺失

**用户原话**：「做一个待办事项应用」

```markdown
## 需求梳理

**一句话目标**：一个人在手机上快速记下今天要做的事，做完划掉。

**使用者与场景**：你自己，碎片时间记录，一天看几次；不需要给别人看。

**功能清单**
- Must：新增一条待办 / 勾选完成 / 未完成与已完成区分显示 / 删除
- Should：本地存储，刷新后还在

**非目标（这次不做）**：不做账号与多用户、不做提醒推送、不做子任务和标签分类、不做日期视图。

**验收标准**
- [ ] 输入框回车后新条目出现在列表顶部
- [ ] 点击条目左侧圆点，条目变成划线态并落到已完成区
- [ ] 刷新页面，之前写的条目还在

**待确认**（最多 3 条）
1. 要不要"今天/全部"两个视图？——我按单一列表先做了，条数多了再加。
2. 数据存哪？——我按浏览器本地存储（localStorage）做的，换设备不同步。如果你要跨设备，告诉我。
```

**要点**：这句话最大的缺口是"给谁用"。默认成"给用户自己用"，于是账号、提醒、协作这三样最容易被期待的东西
必须写进非目标——不写，用户看到成品就会问"怎么不能提醒我"。

## 例 2：范围过载

**用户原话**：「做一个像 Notion 的笔记软件，能有数据库、看板、协作，还要好看」

```markdown
## 需求梳理

**一句话目标**：先做一个能用的单页笔记：能建页面、页面里能写结构化内容。

**使用者与场景**：你自己在浏览器里写，先验证交互和排版，不是给人多人协作。

**功能清单**
- Must：左侧页面树（新建/重命名/删除）/ 右侧正文编辑（标题、列表、待办、代码块四种块）/ 自动保存
- Should：正文里能用 `[[` 引用另一个页面

**非目标（这次不做）**：不做多人协作与权限、不做数据库视图（看板/表格/日历切换）、不做模板系统、不做导入导出。
这一轮只做"页面树 + 块编辑器"这一条主干。

**验收标准**
- [ ] 新建页面后立即出现在左侧并可写入
- [ ] 四种块能互相切换且顺序保持
- [ ] 关闭标签页再打开，内容还在

**待确认**（最多 3 条）
1. 上面四个非目标里，哪个是你这次真正要的？——我全做了取舍，如果"看板"才是重点，请告诉我，那主干就要换掉。
2. 数据存哪？——暂时 localStorage，够一个人用。
3. "好看"有参照物吗？——我按极简风（大字距、无侧栏装饰）做的，有喜欢的截图发我。
```

**要点**：这类需求的缺口不是"少"而是"多"。梳理的价值就是**把砍掉的东西写明**，
把一次注定失望的交付变成一次可以反驳的清单。用户指着"非目标"说"这个要"，比看到成品说"这不是我要的"便宜得多。

## 例 3：判据缺失

**用户原话**：「帮我做个天气查询页面，要炫酷」

```markdown
## 需求梳理

**一句话目标**：输入城市名，看到当前天气和未来几天，视觉上有一个动效主视觉。

**使用者与场景**：演示用，打开就能出效果，不需要真实用户流量。

**功能清单**
- Must：城市输入并查询 / 当前温度与天气图标 / 未来 5 天列表 / 一个动态背景（随天气状态变化）
- Should：记住上一个城市

**非目标（这次不做）**：不做定位自动获取、不做逐小时预报、不做多城市对比收藏。

**验收标准**
- [ ] 输入"杭州"能看到温度与未来 5 天
- [ ] 切到下雨的城市，背景动效跟着变
- [ ] 查不到城市时有明确提示，不出现空白页

**待确认**（最多 3 条）
1. 天气数据用真实 API 还是演示数据？——**这条会决定整个页面的结构**。我按演示数据（内置几个城市）做的，
   点开即出效果、不需要 key。如果要真实数据，需要你提供 API key。
2. "炫酷"是动效多还是留白精致？——我按前者做的。
```

**要点**：接口类需求的第一问永远是**数据从哪来**，因为它是唯一一个"选错就要重写"的决策，
所以要标出来、并说明按哪个方案先做了。其余含糊的形容词（"炫酷"）不要追问定义，
直接选一种实现写进"待确认"——形容词是看不出台词的，看到成品才能反馈。

## 三个例子共有的形状

1. 一句话目标里**暗含了使用者**（"一个人"、"你自己"、"演示用"），这是最省沟通的地方。
2. 非目标的条数通常不少于 Must —— 这是这个模板跟普通需求列表最大的区别。
3. 每条"待确认"都自带一个**已经做出的选择**。用户不回也能继续，回了就是明确的修改指令。
