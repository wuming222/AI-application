# 需求梳理（动手之前）

用户提的需求越短，返工越多。"做个待办应用"这句话里，使用者、场景、核心动作、边界全都缺。
本技能做的事只有一件：**在开始产出之前，把这些缺口暴露出来并填成一个用户可以指着改的东西。**

**本技能不做什么**：不写代码、不创建文件、不执行命令、不做技术方案选型、不连环追问十个问题。

## 什么时候用

- 用户的要求是一句话，且这句话可以有 **两种以上合理实现**（这时值得梳理）。
- 用户明确要求"先梳理/先想清楚/帮我列需求"。
- 需求已经具体到"照着做不会做错"时，**不要用**——直接产出，梳理反而拖慢。

## 唯一动作：产出需求梳理块

按下面的模板输出一次，放在正式产出之前。输出完**继续往下做**，不要停下来等回复，
除非第 5 段里有问题属于"问错了方向整个交付就废"的那一类。

```markdown
## 需求梳理

**一句话目标**：{给谁用的，用来解决什么}

**使用者与场景**：{谁、在什么设备上、什么时候用、用完去做什么}

**功能清单**
- Must：{没有就不算完成，2-5 条，每条是一个能演示的动作}
- Should：{有更好，明确可以后做，0-3 条}

**非目标（这次不做）**：{2-4 条，必须是用户可能真的会以为包含的东西}

**验收标准**
- [ ] {可观察、可判真假的条件}
- [ ] ...

**待确认**（最多 3 条）
1. {问题}——我按 {假设} 先做了，如果不是这样告诉我改哪里。
```

## 三条纪律

### 1. 一次最多问三个，其余用假设兜住

追问的成本由用户的注意力付。问十个问题的结果是用户一个都不答。
判据：**"这个答案会不会改变我接下来 10 分钟做的东西？"** 会 → 值得问；不会 → 自己定，写进"待确认"并说明按什么假设做的。

### 2. 缺的信息要标成假设，不要假装知道

"非目标"这一段的唯一作用是**替用户否掉他没说的东西**。写"暂不做多用户协作"比写"支持多用户协作"更有用，
因为它把一次沉默变成了一个可以反驳的陈述。想不出非目标，说明需求还没读到关键处。

### 3. 验收标准要能判真假

写"- [ ] 能添加一条待办并在列表看到"，不写"- [ ] 交互流畅"。
后者无法核对，等于没写，而且用户没法用它来指出你哪里做得不对。

## 常见的四类缺口

拿不准漏了什么时，逐个问自己这四条（不必都写进输出，只用于自查）：

1. **谁用** —— 用户自己演示给别人看，还是给一个真实的人日常用？后者要管数据存哪。
2. **数据从哪来、活多久** —— 刷新还在不在？换设备还在不在？
3. **核心动作是哪一个** —— 一句话需求里通常藏着 1 个主动作和 3 个附属动作，只做主动作就够看效果了。
4. **什么算完成** —— 用户会不会看着成品说"这不是我要的"？会的话说明这条还没定。
