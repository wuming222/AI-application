### 关键设计判断（不是风格取舍，记下来免得被顺手改回去）

1. **一个开关只允许有一个判据处**。去掉总闸之后，"这一家开不开"必须**从逐技能开关集派生**，不能再存一份布尔值 —— 那是第二个真相源。为此给 `CapabilitySourceInfo` 加了可选 `resolveEnabled()`，`capabilityStore.recompute()` 优先走它、派生时不读存值。
2. **#17 的修法是把两处判据合成一处，不是给第二处补一个 if**。常驻索引段与工具定义现在都读同一个 `enabledNames.length`；各判一次就是 09-19 那个缺陷的成因，补 if 只会在下次改开关语义时再漏一次。
3. **旧的"总闸关过"必须翻译成"逐技能全关"**。`legacyMaster` 一次性迁移：读到旧值为 `false` 就清空开关集并落盘。不翻的话，他先前明确关掉的技能会在升级后自己亮起来 —— 丢一份名单比这轻。
4. **内置优先，且内置不受上游成败影响**。百炼列表失败只能让百炼那几家消失；同名时内置赢，被遮蔽那条以 error 报出来不静默丢弃。目录 / 正文 / 引用三处解析共用同一个 `_open()`。
5. **关掉的那一个要指名道姓地回**。三条拒绝路径分开：整家关 / 只关这一个（带技能名 + 指向面板）/ 目录里没有。只说"未启用"，模型会当成服务故障接着试第二个名字。

## 11. 未来需求：多租户定位确定后的排序与拆法

### 前提（当天三次收敛，最终形态记在最后一条）

定位是**别人能注册进来用的服务**。此前 `sessions` / `messages` / `workspaces` 三张表零用户维度，而此前所有架构决定的隐含前提都是"单用户本机工具"。

当天关于身份拍了三次：

1. 先定"MVP 阶段登录允许粗糙"；
2. 再定"换设备找回先不做"——据此我曾把 P0 压成匿名设备身份（一个浏览器 uuid，不要密码），真账号整节降到 P1；
3. **最终定：注册必选 + 找回密码靠人工。** 于是第 2 条那套匿名层整个删掉，"真账号"并回 P0-A。

### 关键拆法：把"隔离"和"找回"当成两件事

这两件事的成本差一个量级，混在一起谈的结果是一直不动：

| | 解决什么 | 需要身份 | 需要密码 |
|---|---|---|---|
| **隔离** | 陌生人互相看不到对方的会话与代码 | 要（一个可辨识来源即可） | **不要** |
| **找回** | 换设备／清缓存后仍能拿回自己的东西 | 要 | 要 |

拆法本身仍然成立，但第 3 次收敛之后结论变了：**注册必选意味着隔离直接拿真账号做**，不必先做便宜的 uuid 层再迁移。剩下的"粗糙"全部落在找回这一格上——见下面的通道盘点。

### 找回为什么只能是人工：把通道盘一遍

日常产品的"忘记密码"能成立，靠的是一个**本来就能证明你是你的出带通道**（点一下链接 = 证明邮箱是你的）。这个通道本项目一个都没有：

| 通道族 | 本项目可用性 |
|---|---|
| 邮件 / 短信 / authenticator 验证码 | 要接服务商、要配额、要防轰炸。当天明确不接 |
| 只有你知道的秘密（恢复码、密保问题） | 免费，代价是用户得长期保管一样东西。**当天明确否掉**（"恢复码也太麻烦了"） |
| 一个人给他担保（站长手动重置） | 免费，MVP 阶段唯一的"运营"就是我自己 |

取第三条。具体形态：前端一句"忘记密码？联系 xxx"的文案，服务端一个**只能本地跑的命令行脚本** `python -m app.scripts.reset_password <username> <newpassword>`。刻意不走 HTTP——一旦是接口就有鉴权问题（谁能调？调了要不要验身份？），而文件权限本身就是那道验证，且零新增攻击面。

顺带定死一条不能省的：**"用户名已存在"只能在注册时出现**。如果登录接口在"查无此人"和"密码不对"上返回不同信息，它就是个用户名枚举工具；这两支要合成一句"用户名或密码不对"。

### P0-A 账号 + 数据归属（注册必选）

**实测现状**：`routes/sessions.py` 8 个端点、14 条 SQL 语句（关键字命中是 17，多的 3 处是 `ON DELETE CASCADE` 与 upsert 里的 `DO UPDATE`，不是独立语句）。归属要落在 **9 条**上：`:43` `:55` `:71` `:79` `:89` `:129` `:143` `:166` `:178`。

最干净的三处泄露：

- `:43` `GET /api/sessions` —— SELECT 无任何过滤，任何人拿到全部标题；
- `:101` `GET /{id}/messages` —— 直接按 `session_id` 查，**连会话存在性都不验**，拿到 uuid 即可读整段对话；
- `:155` `GET /{id}/workspace` —— 无行时返回 `{files:{}}`，把"不存在"和"是别人的"混成同一个静默空。

`messages` 与 `workspaces` 都以 `session_id` 外键挂在 `sessions` 上，所以**只有 `sessions` 需要加列**，那两张表经会话继承归属（`:59` `:138` `:173` 三条写入都在已校验会话之后，不用改）。

**改法**（文件级）：

1. `database.py`：新增 `users(id, username UNIQUE, pass_hash, created_at)` 与 `auth_tokens(token PRIMARY KEY, user_id, created_at, expires_at)`；`sessions` 加 `user_id TEXT`。沿用现有那个 `try: ALTER … except OperationalError: pass` 的轻量迁移形状。
2. 密码哈希用 stdlib `hashlib.scrypt`，符合"不新增 Python 运行期依赖"。token 用 `secrets.token_urlsafe(32)` 生成的不透明随机串，**不用 JWT**——自证 token 无法撤销，登录态在粗糙阶段反而是负资产。MVP 把 token 原文存表里可以接受（`app.db` 是本机文件、已 gitignore），但**要在此注明：迁到远端数据库前先改成存 hash**。
3. 新增 `routes/auth.py`：`register` / `login` / `logout` / `me` 四个端点，加一个 FastAPI 依赖 `current_user` 从 `Authorization` 头解出 uid；`sessions.py` 那 8 个端点全部挂这个依赖。
4. 归属校验：一个共用小助手 `_owned_session(conn, sid, uid)`，`:101` 与 `:155` 两处跨表读改成"先过助手再读"，其余 9 条在原语句上补 `AND user_id = ?`。
5. `PATCH`（`:67`）与 `DELETE`（`:86`）已把 `cur.rowcount == 0` 当 404 抛，加条件后自动得到"别人的会话 = 404"，不泄露存在性，零额外代码。

**验收**：两个账号，A 建会话后 B 的列表里没有它；B 拿 A 的 session uuid 打 `/messages` 与 `/workspace` 都得 **404 而不是空对象**（这条要单独断言，静默空是最容易放过去的形态）；未登录的写请求 401；登录时"查无此人"与"密码不对"返回体完全一致；`reset_password` 脚本改密后旧 token 立即失效（**这条要断，否则改密只是加了个并行入口**）。

**注册必选换掉了四件事**（相对匿名 uuid 方案）：设备 uuid 及其 try/catch、首访自动建行的迁移分支、归属为空的孤儿行、以及"绑定时把这个 device 的 `sessions.user_id` 改指真账号"那一步。少一条鉴权路径，也少一类"注册完刷新发现会话全空"的 bug 形态。

**粗糙的边界**（明确不做，不是忘了）：邮箱验证、找回密码 UI、权限分级（所有账号同级）、计费与支付。

### P0-B 花费闸门：这轮只记账，不拦

真正花钱的是 **5 个入口**，全部用服务端那把 key：`llm.py:55`（chat/completions）、`:61`（responses）、`:71`（title）、`voice.py:19`（WS → DashScope ASR）、`mcp.py:77`（/call）。

> **当天决定：暂不设限。** 现在还在调试期，闸门唯一会挡住的人是我自己。但**接缝要现在留**，理由不是"以后要加功能"，是"以后要在 5 个地方各插一次判断"——那种分散插入才是重构，而记账与拦截分成两件事之后，打开闸门只是一个配置动作。

闸门单位取**每人每天的生成轮数**，不取 token。理由是 token 计量本身至今未校（`26-9-19.md` 第 10 节里唯一还活着的未验证项），拿一个没测准的量当闸门是假精确。计数 key 用 P0-A 的 `user_id`。

**接缝的最小形态**：一个 `spend_log.record(user_id, entry)` 只记不判，`entry` 就是上面 5 个名字；返回 `None` = 放行。存哪先不定死（表还是内存），因为"MVP 重启后计数清零"在当前阶段完全无害，不值得为它先建表。**记账先行还有个副产品**：等真要定上限时，"单个用户一天实际跑多少轮"是有真实分布可看的，上限就能从用量反推出来，而不是拍一个没出处的数。

**验收（这轮只做前两格）**：

| 场景 | 期望 |
|---|---|
| 配置无上限 | 5 个入口全量放行，且每次调用留下一条带 `user_id` + entry 的记录 |
| 同一用户连续 N 轮 | 计数单调到 N，跨天自动归零 |
| 超限（将来） | 429 + 一句"今天用完了"，**只拒该账号，不影响别人** |
| 未登录（P0-A 之后） | 401，且不进计数 |

**这轮不做**：按 token 计量、计费、支付。

### P1-A 部署耦合

`main.py` 的 CORS 白名单硬编码 `localhost:5173~5178`，`VITE_API_BASE_URL` 也写死 localhost。任何真实域名都要同批改这两处加两端 `.env`，否则症状是"页面能打开但所有接口失败"，且前端不报网络错（见 AGENTS.md 已知坑里 `/api/mcp/*` 被回成 SPA 外壳那一条）。注册公开之后这一项就从"以后再说"变成"上线前必修"，它和 P0-A 是同一批的。

### 当天追问澄清的四件事

**1. "清缓存"的确切含义**：用户手动清站点数据、用无痕模式、换浏览器或换设备。后果不是"数据被删"，是**登录态没了**。在注册必选的模型下这个症状从"我的会话怎么没了"降级成"重新登录一次"——数据一直在库里，只是浏览器不再携带凭证。仍然留一条记账：账号本身丢了的行（人不来了、也没来找你重置）就是永久孤儿行，**库只会涨不会删**，不要将来当新 bug 查。

**2. "用户数据进库"这件事已经做了大半**。会话正文与工作区代码本来就在库里（证据：`skillsProvider.test.ts:295` 断言 `chat-messages` 必须为 `null`，即正文从不落 localStorage）。真正不在库里的只有 4 个偏好/布局 key：`capabilities-enabled`、`skills-selected`、`session-order`、`sidebar-width`。所以 P0-A 缺的不是新表，是 `sessions` 上那一列归属。

**3. 那 4 个偏好仍然不搬进库**，但理由换成账号模型下成立的那一条：搬进库要给用户偏好建表，而 `skills-selected` 是派生开关的**唯一判据源**（见本文上面"关键设计判断"第 2 条，与 AGENTS.md 那条"一个开关只允许有一个判据处"），一旦落库就多出"本地存一份、库里一份，以哪份为准、什么时候同步"的第三个判据处。MVP 的代价可以接受：换浏览器要重新勾一遍技能。

**4. `claim_code` 现在不做，而且不再列入"以后"**。判据是**后补需不需要历史信息**：`user_id` 后补是贵的，因为存量行的归属信息已永久丢失，不可逆；`claim_code` 后补是便宜的，`database.py` 里再套一个 `try: ALTER` 即可，不依赖任何历史数据。所以"现在便宜、以后贵"这条只适用于前者，不要泛化。何况找回已经决定走人工重置，那格需求目前没有主人。

### 与前面需求的关系

RAG 的语料问题因为定位确定而有了答案：语料 = **用户自己的历史会话产物**，且必须按 user scope，所以它结构上只能排在 P0-A 之后（P0-A 一做完，user scope 的 key 就是现成的）。框架文档类语料不必走 RAG —— skill 通道已经在做同一件事，而且是人工精炼过的版本，效果优于自动切片。
