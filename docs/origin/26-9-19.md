### 1. 阿里云那侧的 skill 到底怎么分发（全部真机实测，零模型 token）

分发入口是 **AgentExplorer HTTP API**，不是 MCP、不是 SDK：`https://agentexplorer.aliyuncs.com`，三个只读端点。

| 端点 | 实测 | 说明 |
|---|---|---|
| `GET /openapi/for-agent/categories` | **200 / 6,039B / 0.42s** | 17 个一级分类 + 100 余个二级（`code`/`name`/`children`） |
| `GET /openapi/for-agent/skills?keyword=&searchMode=semantic&maxResults=&categoryCode=&nextToken=` | **200 / 12,144B / 0.34s**，`totalCount=8` | 语义检索与分类列举共用；分类列举模式支持 `nextToken` 分页 |
| `GET /openapi/for-agent/skills/<skillName>` | **200**，正文在**顶层 `content` 字段**（不在 `data` 里） | 返回该 skill 的 `SKILL.md` 全文 |

必带两个头：`User-Agent: AlibabaCloud-Agent-Skills/<caller>`、`x-acs-version: 2026-03-17`。

- **无鉴权**：以上所有请求都没带 AK/SK、没带签名，匿名 200。这点和 MCP 那次根本不同（MCP 的 `LLM_API_KEY` 必须留在服务端）。
- **CORS 全开**：预检与简单请求都回 `Access-Control-Allow-Origin: *`、`Access-Control-Expose-Headers: *`。所以**浏览器可以直连**这个目录，不必须走后端代理。
- 中文 `keyword` 可用（`把本地文件同步到 OSS` → 200，命中 `alibabacloud-oss-manage-cron-upload` 等）。坑在本地环境不在服务：Git Bash 里 `curl --data-urlencode '中文=…'` 会被编码成 `RequestParameterMalformed`（HTTP 400，Aliyun POP 错误体），换成 python `urllib` 就正常 —— 记录进 SDD 的验证脚本一律用 python 发。
- 列表项字段（决定目录里能展示什么）：`skillName` `displayName` `nameEn` `description`（**内含触发词列表**）`descriptionEn` `categoryCode/Name(+En)` `subCategoryCode/Name(+En)` `githubPath` `likeCount` `updatedAt`。
- 目录规模（**逐个 `categoryCode` 翻页取全后去重**）：**297 个唯一 skill**。分类分布：`others` 54、`security` 44、`analyticscomputing` 36、`playbooks` 28、`aiml` 23、`database` 22、`storage` 21、`developertools` 15、`computing` 14、`migrationom` 11、`middleware` 8、`mediaservices` 7、`entcmc` 6、`netcdn` 3、`doweb` 3、`container` 1、`solutions` 1、`eucp` 0。
  > 这个数必须是"翻页取全"的：第一版只按 `totalCount` 估了 296，而更早两次跑（分页游标串类目 + 吞掉 HTTP 400）只拿到 189 / 154 条 —— 部分拉取会把索引成本**低估一半以上**。脚本里已加断言行数守卫（"少于 297 说明有类目没取全，本次结果作废"）。
  >
  > **重跑观察（同日，写 SDD 之后）**：`node_modules/.scratch/skill_budget_probe.py` 再跑一次只得 **269 条**，原因是 `categoryCode=playbooks` 这次返回 **HTTP 400**，该类目贡献 0 条（上一次它贡献 28 条）。所以 **297 不是常量**：它会随上游抖动、也可能随下架而变小。**守卫不能写成"少于 297 即作废"** —— 那样上游一次抖动就让服务端永远拿不到目录。正确口径是两条独立断言：①**逐类目**都要么成功要么明确记进 `errors`，不允许"400 被吞成 0 条"；②总数与"上一次成功结果"比对，跌幅超阈值（建议 >10%）才拒绝并回退旧缓存。阈值是**比例**不是绝对值，与 K2 的口径一致。
- 对照仓库本身：`aliyun/alibabacloud-aiops-skills` 的 master tarball 里有 **349 份 `SKILL.md`**、384 个含 `references/` 的包。即 **AgentExplorer 只上架了仓库的一部分**（297 / 349）。未上架的那部分能否仍按 `skillName` 从详情端点取到正文，**未测**（不要拿"能"当假设）。

探测脚本（都在 `node_modules/.scratch/`，`pnpm install` 会清掉，重建按 AGENTS.md 坑 6 的描述）：
`skill_catalog_smoke.py`（端点/鉴权/CORS 冒烟）、`skill_content_size.py`（正文字节分布）、`skill_index_tokens.py`（三种估算口径对照）、**`skill_token_truth.py`（真分词，本节与第 8 节所有 token 数的唯一来源）**。最后一个依赖 `tiktoken`（`python -m pip install tiktoken`）——**仅诊断用，不进 `pyproject.toml`、不进项目依赖**。

### 2. 一个 skill 是什么形状（这条决定了能不能照抄 MCP）

以**全量 349 份 `SKILL.md`**（仓库 master tarball，tiktoken `cl100k_base` 逐份真分词）为样本：

- **正文体积**：真 token **p50 4,590 / p90 7,846 / p95 9,913 / 最大 22,387，均值 5,031**。字节口径 p50 18,851B / p90 31,107B / 最大 72,271B。中文占比中位只有 **0.1%**（正文是写给模型看的英文操作手册），所以正文按 ÷3 估算反而**偏高 26%**（真值 ≈ 3.78 字符/token）。
  → 结论比第一版更乐观也更可控：**一份 p50 正文 = softLimit 的 8%**（第一版按 ÷3 说 12%）。真正的问题不是"一份装不下"，而是"装三份最坏就吃掉 95%"（第 8 节 K5）。
- **官方规范的满足率（拿真分词复核，不是宣称）**：`<500 行` 只有 **10/349 = 3%** 违反；`正文 <5,000 token` 建议 **148/349 = 42% 违反**（同一件事按 ÷3 估会得出 62%，估高了）。也就是说：**行数这一条他们基本守住了，token 这一条接近一半超出**。首期若照抄"一份 SKILL.md 整段注入"，就要接受 p90 单份 7,846t、最大 22,387t（softLimit 的 37%）。
- **多文件包，不是单条 prompt**：384 个包含 `references/`，**单 skill 的 references 个数 p50 5 / p90 13 / 最大 482**，总字节 **p50 31,517B / p90 108,319B / 最大 1.23 MB**；`(SKILL.md + references) / SKILL.md` 的体积比 **p50 2.6x / p90 6.7x / 最大 21.9x**。另有 938 个 `scripts/*`（`alibabacloud-bailian-memory` 一份带 15 个 py + `requirements.txt`）。**没有任何一个包只有 `SKILL.md`**。
  → 正文里那些 `见 references/ram-policies.md` 是**普遍存在的**（每个包都有 5 个以上附属文件），不是边角情况。这条直接翻掉了第 6 节原先"首期不跟 references"的默认取值。
- **附属文件完全可以枚举**（订正第一版）：`api.github.com/repos/aliyun/alibabacloud-aiops-skills/git/trees/master?recursive=1` 匿名返回整棵树带每个对象的大小（60 次/小时）；`codeload.github.com/.../tar.gz/refs/heads/master` 一把请求 13.4 MB 拿到全部内容；单个文件走 `https://raw.githubusercontent.com/aliyun/alibabacloud-aiops-skills/master/<githubPath>`（实测 200）。第一版那句"`contents` 端点 404 所以拿不到清单"是我把 URL 拼错造成的假故障。

### 3. 与本项目的能力错配（先说结论：不能照抄 MCP 的方法）

MCP 那次能"接进来就能用"，是因为 MCP 工具本身就是**一个 RPC 端点**：前端把参数交给 `POST /api/mcp/call`，服务端替它执行，回一段文本。

Skill 不是端点，是**写给"会跑 shell、装了 `aliyun` CLI、持有云凭证、能执行 `python scripts/*.py`"的 agent 看的操作手册**（实测正文里满篇 `aliyun ecs Describe…`、`powershell -NoProfile -Command "curl.exe …"`、`pip install -r scripts/requirements.txt`）。本项目 agent 的执行面（`packages/web/src/agent/toolRegistry.ts:26`）只有：

- 虚拟文件系统的 5 个工具：`write_file` `read_file` `list_files` `delete_file` `edit_file`（`toolRegistry.ts:66-256`，全在内存 Map，见 `packages/web/src/store/workspaceStore.ts:30`）；
- MCP 外部工具（`toolRegistry.ts:268` 注册）；
- 产出形态是前端代码 + 右侧 iframe 预览。

**没有任何命令执行工具，也没有 Node/Python 运行时**（`AGENTS.md` 架构地图所列文件即全部）。所以"skill 里的动作由谁执行"必须先回答，否则接进来只是一堆模型读得懂、但落不了地的说明书。

### 4. 候选路线（推荐 A + 预留 C）

| 路线 | 做什么 | 代价 | 残留风险 |
|---|---|---|---|
| **A 知识注入**（推荐首期） | 接目录 + 检索 + 按需取全文；skill 只作为**提示词与规范来源**，让模型据此产出**产物**（正确的 CLI/SDK/Terraform 代码、参数命名、避坑清单）写进虚拟文件系统或回答里，**不执行** | 前端为主，约等于"再来一次 externalTools"的量级。目录 API 匿名且 CORS 全开，技术上浏览器可直连，**但选择不直连，理由见 7.4** | 用户会以为"接了就能运维云资源"，界面必须写清"只生成不执行"；skill 正文里的执行指令需要一段约束提示词兜住，否则模型会输出"请你手动执行以下命令"式回答 |
| **C 转成 MCP 工具承接动作** | 阿里云另有 MCP Server Core（`CallCLI`、RunScript 等）。**已合入 main 的 MCP 通道**可直接把它当第三个 server 接上；skill 退化为"如何用这些工具"的说明书 | 复用现有 `packages/server/app/mcp/`，增量小 | 需要云侧开通/AK 授权，不是我们这边能自己点开的事；且 MCP Core 的可用性未实测 |
| B 自建执行面 | 后端加沙箱跑 `scripts/*.py` 与 `aliyun` CLI | 是独立子系统：凭证管理、隔离、超时、审计、依赖安装，工作量数倍于 MCP 全程 | 在浏览器产品里放一个能执行任意命令的服务端，风险面完全不同。首期不建议 |

### 5. 落地时的既有机制（逐条读过源码，行号以合并 MCP 后的 main 为准）

2. **上下文预算的真实口径**：`contextBudget.ts:17` `CHARS_PER_TOKEN = 3`（注释写明是设计文档取值），`resolveLimits()` :11-12 默认 **softLimit 60,000 / hardLimit 150,000 token**，可用 `VITE_CONTEXT_SOFT_LIMIT` / `VITE_CONTEXT_HARD_LIMIT` 覆盖。用它换算 skill 会得到**两头都偏**的结论：正文近全 ASCII，÷3 **估高 26%**（真 p50 4,590t = soft 的 8%，不是第一版说的 7,240t / 12%）；索引描述近半中文，÷3 **估低 52%**（真 26,349t = soft 的 44%，不是 12,675t / 21%）。偏差倍数与取值建议见第 8 节 K1。

### 7. 回答"skill 也当工具、和 MCP 统一管理"

**能统一，而且值得统一** —— 现有代码已经有 80% 的通用形状，只是名字里带 `mcp`。但要分清统一的是什么：**管道**（发现 → 注册 → 开关 → 面板 → 进度 → 错误契约）可以统一；**"谁来执行 skill 里的命令"这个问题，统一抽象不解决**，它仍是 A（只注入知识）/ B（自建沙箱）/ C（动作走阿里云 MCP）三选一。

#### 7.1 统一后的抽象

```
capability（一个可被模型调用的能力）
  provider:   'mcp' | 'skill'
  sourceId:   mcp 的 server id（amap-maps） / skill 的 skillName
  name:       带命名空间的工具名  mcp__<service>__<tool> | skill__<name>
  durability: 'transient' | 'durable'      ← 新增维度，见 7.2
  effect:     'data' | 'instructions'      ← 新增维度，见 7.2
  executor(args) → { text, isError }
```

落点到现有代码：

| 现有 | 升级为 | 改动量 |
|---|---|---|
| `meta?: { mcpService?: string }`（`toolRegistry.ts:19`） | `meta?: { provider, sourceId, durability, effect }` | 一处类型 + `getDefinitionsFor` 的 filter 条件，语义不变 |
| `getDefinitionsFor(enabledMcpServices)` | `getDefinitionsFor(enabledSourceIds)` | 改名，调用点 1 处（`runAgentLoop.ts:59`） |
| `agent/externalTools.ts`（清单+注册+开关+快照+订阅） | 通用 `agent/capabilityStore.ts` + `providers/mcp.ts` + `providers/skills.ts` | 通用部分基本是从 `externalTools.ts` 搬；新增 2 个 provider |
| localStorage `mcp-servers-enabled` | 单 key 换名 `capabilities-enabled`，值用带命名空间的 name | 读旧 key 兜一次迁移 |
| `McpServersPanel.tsx` | `CapabilityPanel.tsx`，两组标题：MCP 服务 / 技能 | 组件改造 |

| `buildSystemPrompt`（`runAgentLoop.ts:25`） | 追加"技能目录"段（仅启用项的 name+description，整段带 token 上限，见 K3） | +1 参数 |

**为什么"启用集"仍是索引成立的前提**（第一版这里写的"≈59,000 token = 直接等于 softLimit"是拍脑袋的 200 token/条乘出来的，作废）。真分词口径：单条 `skillName|displayName|description` **中位 89 token**（p90 130 / 最大 224，中文占比中位 48%），**全 297 条常驻 = 26,349 token = softLimit 的 44%、hardLimit 的 16%**。所以"全目录常驻"并非装不下——它确实能进窗口，代价在别处：

`buildSystemPrompt` 在 `runAgentLoop.ts:74-78` **每一轮都重算**，而 `truncateMessages(payload)` 每轮都把这 26,349t 整段重发给上游；`DEFAULT_MAX_ROUNDS = 20`（:10）。**一次用户输入 = 最多 20 轮 × 26,349t ≈ 527,000 token 的重发**，这才是常驻索引的真实账单（同一口径也解释了 Qoder credits 报表里"resend amplification"这一项为什么会那么大）。预算怎么切见第 8 节 K3/K4：**常驻索引封顶在 softLimit 的 10%（6,000t）≈ 最坏 41 条 / 典型 67 条**，不在索引里的其余 skill 由模型 `skill_search` 现搜现取，用户也能在面板里现场勾。这条量化同时解释了第 6 节"勾选集 = 全局偏好"和"只注入索引"为什么必须一起成立。

#### 7.2 两处必须显式分叉（统一抽象里本来就该有、MCP 一期没暴露的自由度）

1. **返回值寿命不同**：MCP 结果是"这一次的事实"，压掉无妨；skill 正文是"之后每一轮都要遵守的规范"。而第 5.4 条说明压缩层**第一个压的就是 tool 轮次**。触发时机取决于装的是哪几份：**最坏三份正文（22,387+17,690+…）= 57,046t 就已经 95% softLimit**，按 p50（4,590t）则要 13 份才撞线，中间还夹着写文件的轮次。不处理的话，正文会在超预算那一刻被**静默**压成一行，模型行为退化且界面毫无提示。→ `durability: 'durable'` 的能力，其结果在 `isCompressible`（`contextBudget.ts:100`）里豁免，并做"同一 skill 只保留最新一份正文"的去重 + 份数上限（K5），防止反复 load 无界堆叠。
2. **返回值会改写模型行为**：MCP 回数据；skill 回一叠 `aliyun ecs Describe…` / `pip install -r scripts/requirements.txt` 的指令，而本应用没有命令执行面。→ `effect: 'instructions'` 的能力，注入正文时同轮附一段约束（把"执行"转译成"产出命令清单/代码产物交给用户"），并在界面标注"只生成不执行"。

#### 7.3 建议首期取 A（**待拍板**，见第 6 节表末行），并把 C 留在 provider 位上

选 A（只注入知识、不执行）。统一管理在这里的红利是：**C（把阿里云 MCP Server Core 当第三个 MCP 能力接上）不再需要新写一套管道**，只要往 `providers/mcp.ts` 加一条 server 配置 —— 但那是外部依赖（要他在云侧开通并授权 AK），单独立项。

#### 7.4 明知可以直连，为什么仍走后端

AgentExplorer 目录匿名 + `Access-Control-Allow-Origin: *`，前端确实能直接 fetch。仍然加 `/api/skills/search`、`/api/skills/content`、`/api/skills/file` 三个只读路由的理由是四条具体的，不是"统一更好看"：

1. **鉴权会变**。今天是匿名，`x-acs-version` 允许的头里已经有 `Authorization`、`x-acs-signature-*`、`x-acs-bearer-token` —— 一旦阿里云侧要求签名，直连方案就得把 AK 放进浏览器，那是不可接受的；走后端只是把 key 留在服务端，与 `mcp/servers.py` 同一纪律。
2. **协议约定不散到前端**。`x-acs-version: 2026-03-17`、UA 约定、`content` 在顶层而非 `data` 下（本次实测踩过一次误判）这些细节收在 `app/skills/` 里，改版本是后端一行。
3. **错误契约只有一套**。与 MCP 一致的"HTTP 恒 200、成败在 body"意味着前端的 `capabilityStore` 不需要为两类 provider 写两套失败处理，也就不会出现"MCP 挂了会显示、skill 挂了静默"的差别。
4. **`references` 要取的是第二个第三方域**。`/api/skills/file` 打的是 `raw.githubusercontent.com`，与 AgentExplorer 不同源；放后端才能把"允许哪些外网域、各自超时多少、`trust_env` 开不开"收进一处（与 `mcp/client.py:43` 同一策略），否则这些会变成分散在浏览器里的两个不可控外部依赖，且还要 raw 域自己回 CORS 头（未测）。

代价：多三个路由、多一跳本机往返（实测目录端点单页 0.34~0.42s，经后端预计再加几毫秒到几十毫秒量级，未单独测）。另一个反向理由也要记着：本机浏览器流量会经过系统代理（`127.0.0.1:7890`，见 `AGENTS.md` 与 MCP 那次的 TLS 教训），走后端能把这个变量收在可配置的一处（`trust_env=False`）。

### 8. 每个硬数字：怎么算的、影响面、改了会怎样

所有 token 数都是 **tiktoken `cl100k_base` 真分词**（`skill_token_truth.py` / `skill_body_thresholds.py`），不是字符换算。上游是 qwen，其对中文的压缩率优于 cl100k，故**中文部分是上界**、ASCII 部分两者接近（正文中位中文占比仅 0.1%，所以正文那组数可信度高）。

**K1 `CHARS_PER_TOKEN = 3`（`contextBudget.ts:17`）—— 全仓预算判断的换算基准**

- 怎么算：拿真分词反推。正文近全 ASCII → **3.78 字符/token**，所以 ÷3 **估高 26%**；索引描述中文占 48% → **1.44 字符/token**，所以 ÷3 **估低 52%**（26,349 真 vs 12,675 估）。
- 影响面：`truncateMessages` 的所有触发时机、阶段一/阶段二是否启动，以及本文件里每一个"占 softLimit 百分之几"的说法。
- 改了会怎样：换成分档口径（CJK 1 字符≈1 token、ASCII 4 字符≈1 token）→ **对索引更晚判定超预算**（真实风险，现在算少了）、**对英文正文更早压缩**（现在算多了，白丢历史）。但它是全局函数，改一次要重跑全部截断单测，且会改变**已有会话**的截断行为（同一份历史在新口径下进出阶段二的时点不同）。
- 首期取值：**不动全局**。新增的 skill 预算判断（K3/K4/K5）一律用真分词换算成"字符"落地（索引按 1.5 字符/token、正文按 3.8 字符/token），并在代码注释里写明这两条比例来自哪里。把"分档估算器"单独立项。

**K2 softLimit 60,000 / hardLimit 150,000（`contextBudget.ts:11-12`，env 可覆盖）**

- 怎么算：现值即默认值；`VITE_CONTEXT_SOFT_LIMIT` / `VITE_CONTEXT_HARD_LIMIT` 覆盖。
- 影响面：skill 全部预算的**分母**。本节的百分比全是相对它说的。
- 改了会怎样：soft 提到 100,000 → 全 297 条目录常驻（26,349t）从"占 44%"降到"占 26%"，看着可行；代价是**每一轮**请求都多带的部分按 K10 的放大系数付账，且阶段一压缩来得更晚、上游计费更贵。soft 降到 30,000 → 索引预算（K3）只剩 3,000t ≈ 最坏 18 条。
- 首期取值：**不动**。skill 侧的所有取值都写成"占 softLimit 的比例"，让它跟着 env 走（K3~K6 同此纪律）。

**K3 常驻索引预算（新）：建议 ≤ softLimit 的 10% = 6,000 真 token**

- 怎么算：单条 `skillName|displayName|description` 真 token **p50 89 / p90 130 / max 224**。按最坏（先取最长的）累加：5 条 1,021t、10 条 1,851t、20 条 3,295t、40 条 5,898t。所以 **6,000t 预算 = 最坏约 41 条 / 按 p50 89t 算约 67 条**。渲染成精简式 `name: description` 能多塞约 15%（全量 22,982t vs 26,349t）。
- 影响面：决定"模型不搜就能看见哪些 skill"。上限内的条目模型每轮都看得到；上限外的只能靠 `skill_search`（0.33s 一次往返）或用户手勾。也直接影响每轮计费（K10）。
- 改了会怎样：10% → 20%（12,000t）≈ 最坏 100 条常驻（覆盖目录的三分之一），代价是一次 20 轮生成多约 240,000 重发 token。10% → 5%（3,000t）≈ 最坏 18 条（实测 20 条已 3,295t），几乎只能靠搜。
- 为什么非要一个上限而不是"勾多少算多少"：勾选项是用户随时可加的，**没有上限时索引段会静默吃进窗口**，直到阶段一压缩把对话历史（含更早的 skill 正文）挤掉，用户看到的现象是"模型开始忘记之前说过的话"，且界面没有任何提示。有上限才能把"放不下"变成面板上的可见约束（勾到上限时禁用并说明）。

**K4 单份 SKILL.md 注入上限（新）：建议 32,000 字符 ≈ 8,500 真 token ≈ softLimit 的 14%**

- 怎么算：349 份正文字符分位 **min 1,222 / p25 12,062 / p50 17,728 / p75 23,884 / p90 30,437 / p95 35,136 / max 70,901**。各阈值的截断率：cap 16,000 砍 57% 的份数（全库损失 26.7%）；**cap 32,000 砍 8%（全库损失 4.1%，p50 完整保留）**；cap 48,000 砍 1%。
- **明确不可复用现成的 8,000**：`mcp/client.py:31` 的 `MAX_RESULT_CHARS` 与 `toolRegistry.ts:5` 的 `READ_FILE_MAX_CHARS` 都是 8,000。用它 → **349 份里 324 份（93%）被砍，全库丢 58.7% 内容，中位数文件只剩 45%**；且截断只能保头（`slice(0, cap)`），丢的必然是尾部章节，而**我们无法预知用户那次任务需要的是哪一节**（正文结构因 skill 而异，未做章节级统计）。这两处 8,000 是为"一次 RPC 返回值 / 一次文件读取"定的，量级假设与"整份操作手册"不同。
- 影响面：单份正文注入后还剩多少空间给对话；超限的 8% 里模型会看到截断标记。
- 改了会怎样：降到 24,000 → 截断率从 8% 升到 25%，单份省约 2,100t；升到 48,000 → 只截 1%，但单份最坏占到 soft 的 20%。
- 截断时必须带尾巴说明，沿用 `client.py:334` 的写法：`（已截断，原文 70,901 字符，此处只有前 32,000，后半部分未接入）`。不允许静默截断，也**不要**在提示里写"可用 skill_file 补齐"——`skill_file` 取的是 `references/`，补不回同一份 `SKILL.md` 的后半段；真要能补，就得再设计一个"按偏移续读正文"的能力（首期不做，先记在这条里）。

**K5 会话内保留几份"durable 正文"（新）：建议 2 份，第 3 份起 FIFO 降级为占位行**

- 怎么算：按最坏（最长的那几份累加）1 份 22,387t = soft 的 37%、**2 份 40,077t = 67%、3 份 57,046t = 95%**、5 份 89,552t = 149%。按 p50 累加则 1/2/3/5 份 = 8%/15%/23%/38%。
- 影响面：与 7.2.1 是同一件事的两面——豁免压缩（不静默丢）× 份数上限（不无界涨）。少了上限，豁免压缩就会变成"正文把历史顶出去"。
- 改了会怎样：3 份 → 最坏情况直接撞 softLimit，阶段二硬截断接管，被丢的是**整组对话**而不是 skill 正文（因为正文已豁免），比不豁免更难解释。1 份 → 多轮任务里模型每轮都要重 load 上一个 skill（每份 0.1~0.3s + 每轮重发）。
- 占位行文案要重写，不能沿用 `summarizeToolRound` 那句"文件内容已存于工作区，需要时用 read_file 获取"——对 skill 不成立，改成"该 skill 正文已移出上下文，需要时重新 skill_load(<name>)"。

**K6 `skill_file` 单文件上限（新）：建议 16,000 字符**

- 怎么算：3,739 个 `references/*.md` 的体积 **p50 3,766B / p90 12,365B / p95 17,468B / max 347,267B**。cap 8,000 → 砍 22%；**cap 16,000 → 砍 6%**；cap 24,000 → 砍 2%。16,000 字符 ≈ 4,200 真 token = soft 的 7%，且这类结果是 `transient`（可压），不占 K5 的额度。
- 影响面：一次能读进多大的策略文档；max 那种 347KB 的文件不封顶会一口吃掉整个窗口。
- 为什么不能没有上限：`references/` 里存在 482 个文件、单文件 347,267B 的极端包，"模型想看就能看"没有上限等于把窗口控制权交给外部仓库。
- 改了会怎样：这条上限是纯风险位，往小调只增加截断率（8,000 → 22%），往大调线性放大单轮成本。

**K7 目录缓存 TTL：建议目录 6 小时、正文不缓存**

- 怎么算：现成参照是 MCP 的 `TOOLS_TTL_SECONDS = 600.0`（`routes/mcp.py:21`，**不是**本文件第一版记的 300s）。skill 目录是人工发布的仓库内容，变化频率远低于运行时数据；全量拉一次目录要 18 次分类分页 + 翻页，实测单次 0.34~0.42s。
- 影响面：新 skill 上架后多久可见；后端对阿里云侧的请求频率。
- 改了会怎样：沿用 600s → 每次开页面都可能重拉全量目录（297 条 ≈ 38,025 字符），对本机是无谓往返；正文若也缓存，仓库更新后模型会照着旧版操作手册产出（云 API 的参数命名变化是真会失效的），所以正文不缓存。
- 待测：全量目录一次拉完的总耗时（本轮只测了单页 0.34s，未测 297 条串起来多久），进 SDD 前补一次。

**K8 超时链：后端 connect 10s / read 30s，前端保持 35s，顺序不能反**

- 怎么算：MCP 侧既有取值 `httpx.Timeout(timeout, connect=10.0)`（`client.py:43`）与前端 `AbortSignal.timeout(35_000)`（`externalTools.ts:21`）；阿里云官方 curl 约定也是 `--connect-timeout 10 --max-time 30`。
- 影响面：错误归因。**前端超时必须严格大于后端超时**，否则永远是前端先 abort，界面只能显示"请求失败"而拿不到后端那条更具体的上游错误。
- 改了会怎样：把前端调成 30s 与后端持平 → 边界上随机出现"到底是哪层超时"，排查成本回到 MCP 一期之前的状态。
- `routes/skills.py` 三个端点都要**恒 200、成败在 body**（与 `/api/mcp/*` 同契约），否则前端 `capabilityStore` 会出现两套失败处理（7.4 第 3 条）。

**K9 skill 不占 `EXTERNAL_TOOLS_WAIT_MS = 2000` 那条等待（`runAgentLoop.ts:11`）**

- 怎么算：那条 race 是为了"MCP 清单异步到达但 definitions 只能在循环开始处定一次"。skill 的 `skill_search` / `skill_load` / `skill_file` 三个工具定义**只依赖代码本身**，常驻索引段走 `buildSystemPrompt`（每轮重算，:74-78），二者都不需要等目录。
- 影响面：首轮延迟。若把 skill 也塞进那条 race，等于给每次生成加最多 2s 的空等。
- 结论：**不要**为了"看起来统一"把 skill 加进 `externalToolsReady()`；provider 注册时机是 MCP 的特例（要握手才知道工具清单），不是通用规律。这条是统一抽象的一个真实边界，写进 SDD 免得实现时被顺手合并。

**K10 常驻成本的放大器是 `DEFAULT_MAX_ROUNDS = 20`（`runAgentLoop.ts:10`），不动它**

- 怎么算：`runAgentLoop` 每一轮都 `truncateMessages(allMessages)` 后整份重发（:79-81），所以**常驻内容按轮次计费**：K3 的 6,000t 索引 × 20 轮 = 一次用户输入最多 120,000 重发 token；K5 的 2 份正文（p50 计 9,180t）× 剩余轮次同量级。
- 影响面：这是"为什么索引只放启用项""为什么正文要有份数上限"的共同理由，也是评估任何"往 system 里多塞点东西"想法的第一道闸。
- 改了会怎样：把上限从"占 softLimit 比例"改成"绝对 token"，就会在用户调低 `VITE_CONTEXT_SOFT_LIMIT` 时失去保护，所以 K3~K6 一律按比例定。

|---|---|---|---|
| P1 | **三级渐进式披露**：① `name`+`description` 常驻，"每个 Skill 只占几十到一百来个 token，所以你装几百个 Skill 也不会有感知"；② 命中才把整份 `SKILL.md` 读进上下文，"文档给的上限是不超过 5k token"；③ `references/`、`scripts/` "平时躺在文件系统上，一个 token 都不占"，需要才读/跑 | ① 成立：单条真分词 **89 token**，正落在"几十到一百来个"里；但"装几百个也无感知"隐含了宿主窗口够大这一未写明的前提（按常见 200k 窗口算，297 条 ≈ 13%，确实无感知），而我们的 softLimit 只有 60,000，同一份索引就是 **44%**。② 只守住 58%（148/349 超 5,000t）。③ 我们没有文件系统，得换成"默认 0 token + 一次工具调用才取" | **借结构，不借额度**：三级映射成 `常驻索引(K3) / skill_load(K4+K5) / skill_file(K6)`；每级的预算按我们自己的 softLimit 重算 |
| P2 | **元数据硬上限**：`name` ≤64 字符（小写字母/数字/连字符）、`description` ≤1024 字符、`compatibility` ≤500、`SKILL.md` <500 行、正文 <5,000 token | 行数这条**实测守住 97%**（10/349 违反），token 这条**只守住 58%**。`description` 上限 1024 字符 = 索引单条最坏 224 token 的直接来源 | **借**：常驻索引的成本上界是他们的元数据约束给的，所以我们不需要自己再截 `description`（那是他们的字段语义），只需要控制**条数**（K3）。**不借**"5,000 token"当我们自己的正文上限——近半仓库都不满足它，照抄会把 p90 的正文全砍 |
| P3 | **脚本代码永不进上下文**："模型执行 `scripts/` 里的 Python 时，脚本代码本身永远不会进上下文，只有运行输出回来。比让模型现场编代码省 token，而且结果确定" | 我们**没有执行面**，所以连"输出回来"这一步也没有；仓库里有 938 个 `scripts/*`，正文里 50% 的份数提到 `scripts/` | **反向借鉴**：这是一条"明确不做"的依据 —— 既然不执行，就不该把 `scripts/*.py` 源码注入上下文（那是最贵的浪费）。取而代之：正文提到脚本时，界面与提示词都要说清"本应用不执行脚本" |
| P4 | **官方推荐命令固定带 `--full-depth`**：`npx skills add aliyun/alibabacloud-aiops-skills --skill <name> --agent <client> -y --full-depth`（`--agent` 支持列表里就有 `qoder`；不带 `-g` 装到 `.{client}/skills/`） | 每个包 p50 有 5 个 `references/` 文件、`(SKILL.md+refs)/SKILL.md` 体积比 p50 **2.6x**；正文里 **96%（335/349）** 出现 `references/` 引用 | **借这个取向，但理由换成我们自己的**。订正：第一版写的"他们的验收标准把非 full-depth 安装判为 Incorrect"**在那份文档里找不到对应表格，撤回** —— 该页只说了推荐命令带 `--full-depth`、没定义"浅装会缺什么"。所以"首期就要供给 references"的依据是**我们这边 96% 的正文都在引用附属文件**（不跟就是让模型照着读不到的文档编内容），不是他们的判定 |
| P5 | **运行前置写在正文里**：文档明确 skill 依赖"aliyun CLI ≥ 3.3.3 且已配置凭证、对应服务已开通、RAM 策略如 `AliyunResourceCenterReadOnlyAccess`"，Agent 的第一步动作是**校验前置** | 我们的 agent 校验不了任何东西（没有 shell、没有凭证） | **借一半**：把"前置检查"这一段的产出物从"执行命令"改成"在回答里列出用户需要自行满足的前置"。这是 7.2.2 约束提示词的具体内容，不是可选项 —— 否则会产出看起来能跑的假动作 |
| P6 | **定位口径**："MCP 解决能调什么工具，Skills 解决怎么把一件事做对；前者是连接层，后者是知识层，两者互补" | —— | **借来给"统一管理"划边界**：管道（发现→注册→开关→面板→进度→错误契约）统一；**语义不统一** —— 不能因为都叫 `capability` 就让 skill 走 MCP 的"调用即返回数据"路径。7.1 里 `durability` / `effect` 两个维度就是这句话的代码化 |

### 明确不做 / 门槛

- 首期不自建命令执行面（路线 B 否）。
- **不把 `scripts/*.py` 源码注入上下文**（P3：他们自己的设计就是"脚本代码永不进上下文"，而我们连执行面都没有；仓库 938 个脚本注进来纯属最贵的浪费）。
- `references` 取不到就要**显式回一条"未找到"**，不允许让模型假装读过。实测正文里 2,074 条去重后的 `references/` 引用有 **15%（315 条）在包里找不到同名文件**（只按文件名比对，已属宽松）——所以断链是**必然发生**的边角，不是理论风险，处理路径必须设计而不是等它出现。
- 不花模型 token 的验证优先；端到端"模型自己选了某个 skill 并按它产出"需要一次真实调用，**照旧等点头**。
- 不引入新的 Python 依赖（MCP 那次保持零新增）。本轮为真分词装了 `tiktoken`，**仅诊断用**：不进 `pyproject.toml`、不进前端依赖、不进任何提交。
- 探测脚本一律用 python 发请求，不用 Git Bash 的 `curl --data-urlencode '中文=…'`（本地编码会造出 400 假故障）。

**进 SDD 前仍未验证的（不要当结论用）**：

1. 上游 qwen 的真实 tokenizer 与 cl100k 的偏差 —— 现在所有"真 token"仍是**代理口径**，对中文偏保守（上界）、对 ASCII 接近。要精确只能拿一次真实调用换 `usage.prompt_tokens` 对账，**等点头**。
2. 全量目录一次拉完的端到端耗时（只测了单页 0.34~0.42s，见 K7）。
3. `raw.githubusercontent.com` 经后端取 `references` 的稳定性（本轮只测过少量单文件 200；系统代理那条变量在 GitHub 域上同样成立）。
4. 未上架的 52 份 `SKILL.md` 能否按 `skillName` 取到正文（P7）。
5. 阶段二硬截断在"正文豁免压缩"之后的实际行为 —— 需要一条构造用例（塞满正文 + 长历史）验证丢的确实是整组对话而不是豁免失效。

### 成立、且被实测复核过的

- **路线 A（只注入知识、不执行）成立**。技能执行器全程不碰 `workspaceStore`：真机跑完 `skill_load` + `skill_file` 后逐会话取工作区，所有会话 `files` 为空。
- **K3/K4/K6 三道闸的形状对，但 K4/K6 的"≤32,000 / ≤16,000"要读成"截断点 + 固定 72 字符提示尾巴"**，即真实上界 32,072 / 16,072（`_clip` 实量：40,000 字符输入返回 32,072）。预算换算用后者。
- **K9（skill 不占 `EXTERNAL_TOOLS_WAIT_MS` 那条 2s race）成立**：三个工具的定义是模块导入时静态注册的，不等清单。真机第一腿在假 LLM 下没有额外空等。
- **K5（durable 豁免必须有额度）成立且必要**：豁免只给最近 2 组；`contextBudgetDurable.test.ts` 5 用例覆盖。
- **"取不到就显式回未找到，不允许让模型假装读过"这条纪律跨通道存活**，内置那家同样靠它（包里没有 `SKILL.md` 时抛 `LocalSkillError`，不返回空串）。

### 当时列的"进 SDD 前仍未验证"五条的下场

1. qwen 真实 tokenizer 与 cl100k 的偏差 —— **仍未测**（要烧一次真实调用，未获授权）。
2. 全量目录端到端耗时 —— **问题变形而不是消失**：百炼一次列表请求拿全量（不再需要 18 次分页 + 翻页）。实测冷取（`invalidate()` 后合成一次）三次 **630 / 637 / 948 ms**，热取（10 分钟列表缓存命中）**≈0 ms**。**样本只有 1 条技能，这组数不能外推到几百条** —— 但它足够说明"每次开页面重拉全量目录"不再是问题，所以 K7 那条 TTL 从 6 小时改成了 10 分钟（技能是用户自己随时会上传/换新版的）。
3. `raw.githubusercontent` 经后端的稳定性 —— **问题消失**（GitHub 域不再是这条通道的上游）。
4. 未上架的 52 份 `SKILL.md` 能否按名取正文 —— **问题消失**（那条目录没了）。
5. 阶段二硬截断在"durable 豁免"之后的实际行为 —— **单测覆盖了**（丢的是整组对话、tool 配对不破），**端到端没有**。真机那 24 项只 load 了一份正文，构造不出"3 份正文 + 长历史"的真实现场。
