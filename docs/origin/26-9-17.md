# 2026-09-17 需求

## MCP 工具接入

### 需求描述

让 Agent 能调用外部 MCP（Model Context Protocol）工具，突破"只能在浏览器内的虚拟文件系统里写代码"这条能力边界 —— 典型动机：取实时信息、查地图/POI、访问用户自己的数据源。

本轮范围只到"基础接入"：把外部工具变成模型可调、进度可见的普通工具。MCP 的 resources / prompts / sampling / elicitation / OAuth 明确不做。

### 查证结果：官方文档给了两条互斥路线

差别不在代码量，而在**工具循环跑在谁那边**。

**路线 A —— 托管式（阿里云侧执行）**

Responses API 的 `tools` 数组里直接放一条 mcp 定义：

```json
{
  "type": "mcp",
  "server_protocol": "sse",
  "server_label": "WebParser",
  "server_description": "网页解析 MCP 服务",
  "server_url": "https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api/v1/mcps/WebParser/sse",
  "headers": { "Authorization": "Bearer <api-key>" }
}
```

- 输出项枚举里确认存在 `mcp_call`；流式侧有 `response.mcp_call_arguments.delta` / `.done`。
- 支持模型含 **Qwen3.8-Flash**，即本项目 `.env` 里的 `LLM_MODEL`。
- 单请求最多 10 个 MCP Server；文档写的 `server_protocol` 当前只有 `sse`。
- 优点：零 MCP 客户端代码、零子进程，后端 `_proxy_to_upstream` 原样转发 JSON 即可，工作量以小时计。
- 代价：`list_tools` 发生在阿里云侧，**我们拿不到工具清单** → 进度 UI 无法预告"要调哪个工具"；执行过程不透明；`abort` 只能断本地 SSE、停不掉远端；只支持 Responses 协议，换供应商即失效。

**路线 B —— 自建式（我们侧执行）**

百炼托管服务同时暴露 Streamable HTTP 端点：`https://dashscope.aliyuncs.com/api/v1/mcps/{Service}/mcp`，鉴权 `Authorization: Bearer {DASHSCOPE_API_KEY}`（与普通模型调用同一把 key）。官方示例即 `mcp` Python SDK 的 `streamablehttp_client` → `session.list_tools()` → 转成 function 格式交给模型，工具调用由**我们自己的循环**发起、结果以 tool result 喂回。

- 优点：工具清单可注入 `registry`，进度渲染、会话分片、落库时机全部沿用现有不变量；工具结果可见、可渲染、可审计；将来接第三方 HTTP server 或本地 stdio server 是同一套代码。
- 代价：MCP 客户端只能落在 FastAPI 侧（stdio 传输要起子进程，浏览器做不到）；新增 `/api/mcp/*` 代理；`ToolRegistry` 需要 `unregister` 与来源标记；信任边界要自己立起来。
- 注意：百炼文档在协议版本上有过迁移（旧 SSE → 新 Streamable HTTP），实际以开通后控制台上给出的端点为准。

两条路线都占用同一个 `tools` 数组，但一个远端执行、一个本地执行，混用会出现"同一能力两条调用路径"的解释困难 —— 建议只选一条。

### 现状与缺口（代码级）

- `toolRegistry.ts:27` 的 `execute` 已支持返回 `Promise<string>`，`ToolContext` 只带 `sessionId` → 动态注册外部工具不需要改 `runAgentLoop`。
- `ToolRegistry` 只有 `register`，没有 `unregister` / 来源标记；外部工具掉线后无法撤定义，模型会继续对着已消失的工具发调用。
- `responses.ts` 已有内置工具事件通道（`web_search` 一类），路线 A 加 `mcp_call` 有先例可循。
- 密钥归属：当前 `VITE_API_BASE_URL` 非空 → 一切走 FastAPI、key 由服务端注入。MCP 的 key（含第三方 server 自带的 key）同样不能进浏览器，localStorage 等于明文可导出。
- 服务开通：百炼 MCP 广场需逐个"立即开通"，WebSearch 这类还有**每月免费额度**，额度用尽服务自动停止 → 需要"未开通/额度耗尽"的界面反馈，不能只报网络错误。

### 已确认（2026-09-17 第一轮需求确认）

1. **路线 B 自建式** —— MCP 客户端在我们侧，工具调用仍由 `runAgentLoop` 发起。理由：保住进度渲染、会话分片、落库时机这套不变量，工具结果可见可审计。
2. **只接百炼托管 Streamable HTTP** —— 端点 `https://dashscope.aliyuncs.com/api/v1/mcps/{Service}/mcp`，鉴权复用 `DASHSCOPE_API_KEY`。不做 stdio 子进程、不做第三方远程 server。
3. **内置 1 个 server，配置写死在服务端** —— 首期不做用户添加界面，密钥不进浏览器。
4. **外部结果只进模型上下文** —— 不允许直接落工作区；写文件仍然只能通过我们自己的 `write_file`，预览 iframe 的信任边界不动。

### 订正：首个 server 不选 WebSearch

上一条推荐把 WebSearch 当成"最自然的第一个 MCP 服务"，这个判断漏看了自己的代码：`responses.ts:73` 已经在每个请求的 `tools` 里硬编码了 `{ type: 'web_search' }`，并配好完整的 `web_search_call` 事件通道（`responses.ts:177-198`）。也就是说联网搜索这条路**已经通了且是托管执行**，再用 MCP 接一遍等于给同一能力做两条调用路径，还比原来多一跳。所以首期 MCP 要选一个**内置工具覆盖不到的能力**，才能证明这条路带来了新能力。

候选：Amap Maps（地点搜索/路线，正好对上"做个附近咖啡馆推荐页"这类需求）、WebParser（把用户给的 URL 变成结构化内容）。

### 已确认（2026-09-17 第二轮澄清）

1. **首个 server = Amap Maps**（地点搜索 / 路线规划），云端托管、试用无需个人高德 key。
2. **模型自主调用 + 一个全局总闸**：默认由模型自己决定是否调用外部工具；另外给一个"停用外部工具"的总开关。它是**全局偏好**（localStorage，按现有约定包 try/catch），不是会话状态 —— 所以不需要进 `bySession` 分片，但要回答"切换开关时正在生成的那一路怎么办"：只影响下一次请求，不追溯当前这轮已注册的工具定义。
3. **结果截断 8000 字符**，与 `READ_FILE_MAX_CHARS = 8000` 同量级；截断时在文末追加一句"（结果已截断）"，让模型知道还有内容没看到。
4. **先真机冒烟再写 SDD**。

### 真机冒烟结果（2026-09-17，探针 `node_modules/.scratch/mcp_smoke.py`，零模型 token）

裸 JSON-RPC 走 MCP Streamable HTTP（`initialize` → `notifications/initialized` → `tools/list`）：

- **端点存活、鉴权正确**：不带 key 返回 401；带 key 返回 404 —— host、路径、密钥都对，只差开通。
- **未开通的错误形态**：`HTTP 404` + JSON-RPC error，message 为中文 `未开通该MCP或非可用开通状态`（`amap-maps`、`WebSearch` 两个 slug 一致）。→ 界面能区分"未开通(404) / 鉴权失败(401) / 网络失败"，不会只甩一句网络错误。
- **开通前拿不到 `mcp-session-id` 响应头**（404 时没有），该头是否必需仍待开通后复测。
- **待开通后补测**：`tools/list` 的真实形状 —— 工具数量与命名（决定 `mcp__<service>__<tool>` 前缀）、`inputSchema` 是否标准 JSON Schema 可直接塞进 `ToolDefinition.parameters`。

### 真机冒烟结果 2：实际开通的是 `antv-visualization-chart`（探针 `mcp_sse_probe.py`）

- **传输形态反转**：`/mcp`（Streamable HTTP）返回 **405** + `current mcp not support streamableHttp`；`/sse` 返回 **200**。也就是说这个服务**只开放旧版 SSE 传输**，第一轮确认的"只接 Streamable HTTP"要改成"两条传输都得支持，至少 SSE 必须支持"。
- **SSE 握手细节（实测可复现）**：`GET /sse` 先推一个 `event: endpoint`，data 是 `message?sessionId=...` 的相对路径；之后每个 JSON-RPC 请求 POST 到那个 URL，**POST 本身只返回 202，真正的回复从 SSE 流里回来**。所以客户端必须"读流 + 发请求"并发，按 `id` 关联回复 —— 这是路线 B 实现里最实质的一块代码，且只能在服务端做。
- 握手成功返回：`protocolVersion 2025-03-26`、`serverInfo {name: "mcp-server-chart", version: "0.8.x"}`、`capabilities` 只有 `tools`（无 resources / prompts，跟我们"只接 tools"的范围正好吻合）。
- **25 个工具，全量体积 53,768 字符**：name 523 + description 4,816 + inputSchema 47,179。工具定义走 `tools` 数组、不在 `contextBudget.ts` 的统计范围内（它只截 messages），但**每轮请求都会重发一次**，最多 20 轮。所以必须做允许清单，否则等于给上下文凭空压进来一份没人看的巨型 schema。工具清单：`generate_{area,bar,column,boxplot,dual_axes,funnel,histogram,line,pie,radar,sankey,scatter,treemap,venn,violin,word_cloud}_chart`、`generate_{pin,path,district}_map`、`generate_{flow,mind,network,organization,fishbone}_diagram`、`generate_liquid_chart`。
- **返回值是公网图片 URL，不是数据也不是代码**：一次真实 `tools/call generate_bar_chart` 返回
  `content: [{ type: "text", text: "https://mdn.alipayobjects.com/one_clip/afts/img/....../original" }]`，无 `structuredContent`、无 `isError`。
  这直接撞上 `runAgentLoop.ts:11` 系统提示词的"CSS/JS 全部内联，**不引用外部资源**"：要用它就得允许生成结果里出现第三方图床 `<img>`；而且**用户提供的数据会被渲染成一张公开可访问的图片地址**（持久性与可猜测性都不可控）。

### 结论：AntV 适合当压力测试，不适合当首个产品能力

Amap 那类返回结构化 JSON（POI 列表），模型可以**自己**用内联代码画图，完全落在现有规则内；AntV 返回的是外部图 URL，等于为了一个图表能力破坏"全部内联"这条产品底线。所以建议：首个内置 server 仍是 Amap（需要你再开通一个），AntV 留着当"25 工具 + 53k schema + SSE 长连接"的白名单与传输压力测试对象 —— 它已经开通、list 不花钱，正好反复跑。

### 真机冒烟结果 3：`amap-maps`（也开通了）

| 项 | 实测 |
|---|---|
| 传输 | **Streamable HTTP 直通**：`POST /mcp` 的 `initialize` → 200；**响应无 `mcp-session-id` 头**，后续请求不带任何会话头也能跑通 |
| 服务端 | `serverInfo {name: "amap-sse-server", version: "1.0.0"}`（名字叫 sse 但走的是 `/mcp`），`protocolVersion 2025-03-26`，capabilities = `logging` + `tools` |
| 工具体积 | **15 个工具，全量序列化仅 5,498 字符**（AntV 是 53,768） |
| 成功返回 | `content:[{type:"text", text:"{\"results\":[{...\"location\":\"120.130396,30.259242\"}]}"}]`，`isError:false`，无 `structuredContent` —— **JSON 装在 text 块里**，不是 image 也不是 resource |
| 失败返回 | `maps_text_search` → HTTP **仍是 200**，body 为 `content:[{type:"text",text:"API 调用失败：USER_DAILY_QUERY_OVER_LIMIT"}], isError:true` |

三条对设计的直接影响：

1. **判定成功不能看 HTTP 状态码**，必须看 JSON-RPC 层的 `isError`；上游（高德）的错误码是一句中文文本，原样回给模型比我们自己造句更好 —— 它会据此改口或换工具。
2. **动态筛的必要性要按体积重新定性**：53k 字符的 AntV 是极端个例，5.5k 的 amap 全量注册几乎没有预算压力。所以"一律筛"换到 amap 上收益近零、却引入"筛漏了就调不到"的新失败模式。建议 SDD 里把筛选做成**按 server 声明**（AntV 开、amap 关），而不是全局一律开。
3. **review 遗留的 MINOR 现在升级为必改**：`AgentToolCallInfo.status === 'error'` 在 `AgentProgress` 里渲染成 ✓（当时判为无害死分支，因为我们的 fs 工具不会走到 error）。MCP 一接进来，`isError:true` 就是常规事件 —— 不改的话每一次上游额度耗尽都会显示成成功。

另外记一笔配额：高德试用配额是共享的，当天 `maps_text_search` 已 `USER_DAILY_QUERY_OVER_LIMIT` 而 `maps_geo` 仍可用。真机验收要预期"部分接口不可用"，不能因为一个工具报错就判定接入失败。

### 已确认（2026-09-17 第三轮，AntV 冒烟之后）

1. ~~**AntV 只做管道验证，不作为产品能力**~~ —— 被第四轮修订为"进产品但默认关"。
2. **传输做 SSE + Streamable HTTP 双支持** —— 实测百炼两个服务形态相反（amap 走 Streamable HTTP、AntV 只开 SSE），所以抽象层必须两种都能跑，不能照文档只写一种。这条不变，且现在有天然测试对。
3. ~~**25 个工具改为"按本轮意图动态筛"**，不用静态白名单~~ —— 被第四轮降级为 v1 不做。当时跟着定的三条硬约束仍然有效，将来补这一层时照用：
   - **筛选只作用于发给模型的 `definitions` 副本**：`registry` 仍是进程级、不区分会话的一次性注册，绝不在每轮请求里 `register` / `unregister` —— 那等于把"本会话本轮的筛选结果"写进全局单例，后台并行的另一路会被污染（AGENTS.md 状态不变量的同类坑）。
   - 被筛掉的工具仍可执行：模型若幻觉调用没发给它的工具，执行比报错更无害（外部工具都只读），进度行照常渲染。
   - **筛选发生在每次 `runAgentLoop` 开始处一次**，不在 20 个 round 之间重算 —— 同一轮用户输入的共同意图不该中途变。

### 已确认（2026-09-17 第四轮，两个 server 都开通之后）

1. **AntV 进产品但默认关闭**，amap 默认启用。
2. **开关形态改成"逐 server"而不是独立总闸**：composer 附件行（`ChatInterface.tsx` 的 `.composer-toolbar` 左侧那组，纸夹按钮旁）放一个入口，点开 `Popover` 列出每个已接入 server 一行 `Switch`。这样只有一个状态源 —— "全部关掉"就是总闸关，不需要再存一份独立的总闸布尔值，也不会出现"总闸开着但唯一启用的 server 被关了"这种自相矛盾的显示。仍是**全局偏好**（localStorage 一个 key，包 try/catch），不进 `bySession` 分片、不落库。
3. **关掉时的语义**：该 server 的工具定义**根本不发**给模型（它不知道有这能力），执行侧同时对外部工具返回一句"外部工具未启用" —— 防的是模型凭上一轮的上下文幻觉调用。
4. **动态筛在 v1 不做**。理由是实测数据：v1 默认只发出 amap 的 15 个工具、5,498 字符，不到上下文软阈值（60,000 字符）的 10%，筛与不筛没有可观测差别，却会引入"筛漏了模型就调不到"的新失败模式，还可能要多花一次模型调用。AntV 那 53,768 字符的极端个例已经被"默认关"挡住了。等真出现"必须默认启用的大 server"时再回来做这一层。

### 顺带抓到的环境问题（与 MCP 无关，但会挡住一切真机验证）

本机注册表开着系统代理 `127.0.0.1:7890`（Clash 类）并在 MITM HTTPS，Python 信任库里没有它的 CA：

| 组合 | 到 `dashscope.aliyuncs.com` 的结果 |
|---|---|
| `httpx` 默认（`trust_env=True`，走系统代理） | `ConnectError: [SSL: UNEXPECTED_EOF_WHILE_READING]` |
| `trust_env=False`（绕开系统代理） | `401`（连通，正常） |
| `trust_env=True` + `verify=False` | `401`（仅用于定位原因，**不作为修法**：关掉证书校验等于放弃 TLS 的防中间人能力） |
| `curl`（不读注册表代理） | `401` |

`packages/server/app/routes/llm.py:17` 与 `:87` 用的正是 `httpx.AsyncClient(...)` 默认值（`trust_env=True`）。因此**真实上游链路当前可能整条挂掉**，而我们这几天一直在用离线假上游验证（AGENTS.md 已知坑 6），所以没暴露。存疑点：正在跑的那个 uvicorn 进程可能继承了不同的环境（启动时 Clash 未开等），要定案得打一次真实请求。修法两条，都不该混进 MCP 分支：国内端点显式 `trust_env=False`，或给系统装 Clash 根证书。
